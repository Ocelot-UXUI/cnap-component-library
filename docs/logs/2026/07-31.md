## 落盘 Workload 资源用量显示与计算原则

Owner 系统描述了资源用量的处理原则：`ResourceQuota` 同时下发带单位字段（`cpu`/`memory`/`ephemeralStorage`）与无单位换算字段（`cpuMilli`/`memoryBytes`/`ephemeralStorageBytes`）；**显示用带单位字段、计算比例用无单位字段**。

新增 `docs/architecture/resource-usage-display-principle.md` 作为强制基线，覆盖：

- 字段映射表（显示 vs 计算）与 `ResourceQuota` 字段语义
- 应用规则：`usagePercent` 直接吃无单位字段、显示直接渲染带单位字符串、高负载判定基于百分比
- 受影响位置清单（`resourceUsage.ts` / `ResourceUsageView.tsx` / `ResourceUsageTooltip.tsx` / `podUsageCells.tsx`）
- 与 `workload-domain-model.md` 的 `ResourceSpec`/`Quantity` 关系（仅覆盖显示侧）
- Open Questions：`cpuMilli`/`*Bytes` 是否所有相关接口都下发；`RuntimeWorkloadContainer.resource*` 是否需补齐

注：上一节的 `resourceUsage.ts` 收窄单位只是显示侧的口径对齐，**比例侧仍违反本原则**（仍解析带单位字符串算比值）。后续需按本文档对齐四个文件，预计触发 plan。

## RuntimeOperation operation name 动态化

Plan: `docs/plans/2026-07-31-runtime-operation-dynamic-name.md`（Status: implemented）。
设计原则：`docs/design/runtime-operation-capability-name-separation.md`（新增）。

**原则**：`RuntimeOperation.capability` 是前端能力标识（路由弹窗），`RuntimeOperation.name` 是后端实现标识（触发 API）。此前 `name` 在 UI 层丢失，API 层硬编码。改造后 name 从接口响应逐层透传到 API 调用点，operation 参数为必填（无默认值），TypeScript 编译器作为安全网。

变更文件清单（~18 文件）：

**Phase 1 - API 层**：
- `src/api/runtimeOperation.ts`：5 个包装函数（`restartWorkload`/`horizontalScale`/`verticalScale`/`restartPod`/`deletePod`）的 Input 接口新增必填 `operation: string`，内部移除硬编码值；`deletePod` 的 force 分支不再内联判断 `'pod.delete-force'` vs `'pod-delete'`，统一使用传入的 `input.operation`。

**Phase 2 - Workload 级弹窗全链路**：
- `WorkloadsHeader/index.tsx`：新增并行 state `activeOperationName`，`handleActionClick` 同时存储 `operation.name` 与 `capability`；onClose 时一并清空。
- `WorkloadsHeader/OperationModals.tsx`：Props 新增 `operationName: string | null`，透传给各 Modal 组件。
- `operations/restart/machine.ts`：Context + InputArgs 新增 `operationName`；submit actor 传入。
- `operations/restart/submit.ts`：`toRestartInput` 新增 `operationName` 参数，输出含 `operation`。
- `operations/restart/RestartModal/index.tsx`：Props 新增 `operationName`，传给 machine input。
- `operations/horizontalScale/` 同上模式（machine + submit + Modal ×3 文件）。
- `operations/verticalScale/` 同上模式（machine + submit + Modal ×3 文件）。

**Phase 3 - Pod 级弹窗**：
- `Workloads/index.tsx`：modal state 类型扩展 `{ key, pods, operationName? }`；行内操作 `handlePodOperation` 携带 `operation.name`；批量栏回调签名改为 `(key, operationName?) => void`。
- `BatchActionBar/index.tsx`：`onAction` 签名改为 `(key, operationName?) => void`；新增 `resolveOperationName()` 从首个 Pod 的 operations 列表按 capability 查找 name 并传递。
- `BatchRestartPodModal/index.tsx`：Props 新增 `operationName: string`，handleSubmit 传入 `restartPod`。
- `DeleteModalBase.tsx`：Props 新增 `operationName: string`，handleSubmit 传入 `deletePod`。
- `BatchPodDeleteRebuildModal/index.tsx` / `BatchPodForceDeleteModal/index.tsx`：接口声明补齐 `operationName`（通过 `{...props}` 自动透传到 DeleteModalBase）。
