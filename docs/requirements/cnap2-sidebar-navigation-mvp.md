# Feature: CNAP 2.0 导航系统 MVP

## Goal

基于 CNAP 2.0 原始设计文档，将当前导航从单层侧边页面菜单演进为可扩展、可被 Agent 理解和调用的应用导航系统。MVP 需要同时覆盖侧边工作区导航、当前工作区二级导航、顶部上下文导航与统一路由元数据之间的协作关系。

## Source Inputs

- `docs/input/source-design-cnap2-CNAP_2.0页面和导航.md`
- `docs/input/source-design-cnap2-CNAP_2.0产品原型设计.md`
- `docs/design/app-overview.md`
- `docs/requirements/route-link-management.md`
- `docs/requirements/route-context-for-llm.md`

## In Scope

- 侧边导航一级入口表达 CNAP 2.0 的工作区概念。
- 当前工作区可展示二级导航，用于进入该工作区下的主要功能页面。
- 顶部导航继续承载账号、应用、环境等业务上下文切换职责。
- 实现简单可用的账号、应用、环境选择器，用于真实驱动导航系统的上下文切换。
- 账号、应用、环境是递进的硬性层级关系：账号包含应用，应用在环境中运行；下层上下文不能脱离上层上下文独立存在。
- 工作区切换不主动清空顶部账号、应用、环境上下文，但目标页面只能消费所属二级路由声明需要的上下文。
- 工作区切换后，MVP 只要求向目标工作区、子应用和具体业务页面提供上次访问时相同的上下文信息；具体业务页面按所属二级路由上下文需求决定使用账号、应用、环境中的哪些信息，完整历史页面内容恢复放到后续阶段考虑。
- 建立可扩展的导航配置模型，新增工作区、二级导航、顶部上下文规则时不需要改动多个分散菜单实现。
- 导航配置应复用统一路由链接管理能力，避免硬编码 URL。
- 导航元数据应能暴露给 Agent，使 Agent 理解“可去哪里、需要什么上下文、如何导航”。
- 侧边导航应支持当前选中态和折叠态。
- 一级工作区按钮可支持状态提示位，MVP 先预留数据结构和展示能力。

## Out Of Scope

- 不实现顶部账号、应用、环境选择器的完整视觉重构，但需要提供简单可用版本。
- 不考虑移动端导航和抽屉菜单。
- 不实现 Ctrl+K / Cmd+K 快捷搜索。
- 不实现真实待审批、进行中变更等状态数量接口。
- 不实现权限驱动的菜单裁剪；MVP 仅保留可扩展入口。
- 不实现所有二级页面的业务功能，只定义导航系统能承载的入口结构。
- 不改变 UUAP 登录、会话、权限校验流程。
- 不把 `data-ai-*` 语义属性纳入本 MVP；AI Agent 如何兜底定位 DOM 和操作 DOM 需要后续单独设计。
- 不替换已有统一路由链接管理与 LLM 路由上下文机制，而是在其基础上扩展导航元数据。

## Navigation System Model

MVP 导航系统由四类信息组成：

- 路由定义：页面 URL 构建和路由参数来源，继续由 `src/routes/` 统一管理。
- 导航结构：工作区、二级导航、辅助入口、分组和默认页。
- 上下文规则：页面是否需要账号、应用、环境，以及顶部导航应显示哪些上下文选择器。
- Agent 元数据：面向 Agent 的导航描述、导航意图、必要参数、上下文要求和可执行动作。

导航配置应成为侧边栏、顶部上下文导航、Agent 路由上下文和后续快捷搜索的共同来源之一，避免每个入口各自维护一份菜单。

导航配置与 `src/routes/` 的关系采用混合方案：`src/routes/` 只负责 route key、path、params、`toUrl()` 和基础描述；navigation registry 负责产品导航结构、上下文需求、层级关系、默认页、回退规则和 Agent 描述，并引用统一 route key 或 route object。

## Navigation Structure

### 一级工作区

MVP 侧边导航应至少包含以下一级工作区：

- 主页：个人 Dashboard 入口。
- 应用：应用列表、应用详情及应用级能力入口。
- 环境：账号下环境管理入口。
- 变更：部署、构建、扩缩容、重启等变更流程入口。
- 资源：集群等基础资源管理入口。
- 账户：账号设置、权限、标签等账号级入口。
- 辅助入口：AI 助手、更新日志、个人设置等可保留在底部或系统分组。

MVP 可暂缓实现“事务”工作区，但菜单结构应允许后续加入待审批、审批记录，并支持红点提示。

### 二级导航

当前工作区激活后，可展示该工作区的二级导航。MVP 二级导航建议范围：

- 应用：应用列表、工作负载、运行配置、应用设置。
- 环境：环境列表、环境配置。
- 变更：部署、流水线、变更历史。
- 资源：集群。
- 账户：账户列表、基本信息、角色和权限、标签。

二级导航应支持分组能力。宽版本可显示分组标题；窄版本可使用分隔线。

### 顶部上下文导航

顶部导航负责快速切换账号、应用、环境等上下文，不承担工作区切换职责。

MVP 不要求完成顶部账号、应用、环境选择器的最终视觉设计，但需要实现简单可用的选择器，使导航系统能够真实运转：用户可以选择账号、应用、环境；页面和导航系统能读取当前上下文；上下文变化能触发页面保活或回退判断。

账号、应用、环境之间存在硬性层级关系：账号是应用的上级，应用是环境相关运行态的上级。系统设计中不能把三者作为彼此独立的并列筛选条件处理。

这意味着：

- 切换账号后，当前应用和环境必须重新校验；如果不属于新账号，应清空或回退到可选择入口。
- 切换应用后，当前环境必须重新校验；如果该应用不能在当前环境下成立，应清空或回退到可选择入口。
- 选择环境时，必须基于当前账号和应用的可用范围。
- 页面上下文需求应表达其最低层级要求：需要应用的页面必然依赖账号；需要环境的页面通常也依赖账号和应用。

MVP 中工作区是一级路由，工作区下对应的二级导航是二级路由。上下文需求配置应放在二级路由层级，而不是按工作区整体固定决定。二级路由以下的三级、四级等子路由必须继承所属二级路由的上下文配置，并且不允许覆盖。

文档不枚举具体二级路由应当配置哪些上下文；代码设计时需要保证不同二级路由可以拥有不同上下文需求，并保证更深层子路由只能继承。

每个二级路由至少应声明：

- 是否需要账号。
- 是否需要应用。
- 是否需要环境。
- 当上下文缺失时的回退页面或选择入口。
- 页面是否应隐藏某些顶部上下文选择器。

## Extensibility Requirements

- 新增一级工作区时，应只需新增一份工作区配置和必要路由定义。
- 新增二级导航项时，应只需挂载到对应工作区配置，并引用统一路由对象。
- 新增二级路由时，应能在同一配置中补充展示名称、描述、所属工作区、上下文需求和 Agent 描述；新增三级及以下子路由时不允许补充上下文需求。
- 导航配置应支持分组、排序、默认路由、图标、禁用状态、提示状态和可选的可见性规则。
- 导航 UI 组件不应内置业务路由判断；应从导航配置派生渲染状态。
- 路由归属、选中态和 Agent 可用导航列表应从同一套元数据推导，避免重复映射。
- 侧边导航布局组件与业务导航项组件应分离；业务组件不包含布局定位信息。

### 父路由与子路由扩展

业务迭代会持续引入新的业务路由。导航系统应允许在父路由或父导航节点基础上便捷加入新的子路由体系，而不是回到 AppLayout 中手写菜单。

推荐的扩展模型是：一级工作区节点声明工作区身份、默认二级路由和回退入口；二级路由节点声明自身上下文需求；三级、四级等更深层子路由继承所属二级路由的上下文需求，不能覆盖。

例如应用工作区下可以有多个二级路由，每个二级路由配置自己的上下文需求；该二级路由下的详情页、编辑页、子流程页等更深层路由都继承该二级路由的上下文需求。

新增子路由时需要补充的信息应集中在导航注册处：

- 父导航 key。
- route key 或 route object。
- 展示名称与分组。
- Agent 描述。
- 二级路由上下文需求；三级及以下子路由不允许声明或覆盖上下文需求。
- 用户意图无法达成时的回退链或兜底 fallback。
- 可选的可见性、禁用、提示状态规则。

父子节点关系应服务于四类派生能力：侧边二级导航渲染、当前路由选中态、Agent 可用导航列表、上下文切换后的保活和回退判断。

## Agent Integration Requirements

Agent 化导航在本 MVP 中只关注结构化导航能力：让 Agent 理解导航目标，并通过统一 route key 和参数执行导航动作。DOM 定位和 DOM 操作的兜底机制暂不纳入本需求。

### Agent 可理解

导航元数据暴露给 Agent 时，应包含：

- 导航目标 key。
- 面向用户的名称。
- 面向 Agent 的简短描述。
- 所属工作区和二级分组。
- 对应 route key。
- 必需路由参数。
- 必需业务上下文：账号、应用、环境。
- 缺少上下文时建议先去的选择页。

### Agent 可执行

Agent 执行导航时，应优先使用统一路由 key 和参数，而不是硬编码 URL。

当用户请求“去应用运行配置”“查看某应用部署”“打开环境配置”等语义导航时，Agent 应能：

1. 从导航元数据中识别目标页面。
2. 判断目标页面需要哪些上下文或路由参数。
3. 在参数充分时调用 navigate 工具直接跳转。
4. 在参数不足时，跳转到合适的列表页或向用户追问。
5. 导航后页面侧边栏和顶部上下文显示正确状态。

## Main User Flows

### 切换工作区

1. 用户点击侧边栏一级工作区。
2. 系统保持当前顶部上下文，不主动清空账号、应用、环境。
3. 系统向目标工作区、子应用和具体业务页面提供上次访问时相同的上下文信息。
4. 如果目标工作区有明确默认页，进入该工作区默认页。
5. 侧边栏更新一级工作区选中态，并展示对应二级导航。

MVP 不要求恢复上次访问页面的完整页面内容、筛选条件、滚动位置或组件内部状态。

### 进入二级页面

1. 用户进入某个工作区。
2. 用户点击该工作区下的二级导航项。
3. 系统使用统一路由对象生成目标 URL。
4. 系统跳转到目标页面，并记录该工作区最近使用的账号、应用、环境上下文。
5. 当前二级导航项显示选中态。

### 顶部上下文切换

1. 用户在顶部导航切换账号、应用或环境。
2. 系统根据当前路由所属二级路由的上下文需求判断用户原本的页面意图是否仍可达成。
3. 如果新上下文仍能达成当前页面意图，系统保持当前页面意图，只替换对应上下文并更新页面数据。
4. 如果新上下文无法达成当前页面意图，系统按回退链逐层回退到更上层的可达导航目标。
5. 如果逐层回退难以判断或仍无法达成，则回退到配置的安全 fallback 页面。

### Agent 发起导航

1. 用户用自然语言提出导航请求。
2. Agent 从导航元数据识别目标导航项和 route key。
3. Agent 判断是否已有必要参数和上下文。
4. 参数充分时，Agent 调用 navigate 工具跳转。
5. 参数不足时，Agent 进入选择页或向用户追问。
6. 跳转后导航系统显示正确的工作区、二级导航和顶部上下文状态。

## Context Switch Preservation And Fallback

顶部上下文切换后的页面保活和回退，是导航系统在账号、应用、环境变化后，根据当前路由所属二级路由的上下文需求，判断用户原本的页面意图是否仍可在新上下文中成立；若成立，则保持当前页面意图并替换上下文；若不成立，则逐层回退到更上层的可达导航目标，最终可用安全 fallback 页面兜底。

“页面保活”保留的不是原始 URL 字符串，而是用户正在表达的页面意图。例如用户在某应用某环境的工作负载页，切换到另一个该应用可用的环境后，仍停留在工作负载页，只是展示新环境的数据。

“回退”发生在新上下文无法支撑当前页面意图时。例如用户在某应用运行配置页切换到另一个账号，而该账号下不存在当前应用，则当前应用运行配置意图无法达成，应优先回退到应用工作区中更上层的应用列表或其他可选择入口。

回退策略不按固定档位区分。理想策略是沿导航层级和业务意图逐层回退：

1. 优先保持当前导航目标。
2. 若当前目标不可达，回退到同一父节点下更通用的目标。
3. 若父节点仍不可达，回退到当前工作区的安全入口。
4. 若层层回退的业务判断在实现上不可行，则使用导航配置中的 fallback 兜底。

示例：

- 应用工作区：工作负载页缺环境时，可回退到应用环境列表；缺应用时，可回退到应用列表。
- 环境工作区：环境配置页切换账号后，如果当前环境不属于新账号，可回退到环境列表。
- 变更工作区：部署详情切换账号后，如果部署不属于新账号，可回退到部署列表。
- 账户工作区：账户角色权限页切换账号后，可保持角色权限页面并展示新账号数据。

MVP 中应先在导航元数据中表达二级路由上下文需求、父子导航关系、回退链和 fallback 页面；完整的自动保活和逐层回退执行可作为后续实现阶段，但文档中的概念和数据要求应提前稳定。

## Business Rules

- 一级导航表示工作区，不应继续无限扩展为平铺页面列表。
- 二级导航只展示当前工作区内的功能，不跨工作区混排。
- 工作区最近上下文应按工作区维度保存；完整页面历史恢复不属于当前 MVP。
- 顶部上下文切换与侧边工作区切换职责分离。
- 账号、应用、环境必须按层级校验和更新，不能作为互相独立的并列状态处理。
- 上下文需求必须由二级路由声明，不能只按工作区粗粒度推断；三级及以下子路由必须继承二级路由上下文配置且不允许覆盖。
- 上下文切换后应优先保持用户页面意图；无法达成时按导航层级和业务意图逐层回退，并最终使用安全 fallback 兜底。
- 导航配置必须引用统一路由对象或 route key，不直接维护硬编码 URL。
- 面向 Agent 的导航描述应来自导航元数据或路由元数据，不应在 prompt 中手写另一份长期列表。
- 账号、应用、环境选择器在 MVP 中需要真实可操作，即使视觉上只实现最小可用版本。
- 当前已有 MVP 页面入口必须仍然可达。
- 业务导航项和布局组件分离，业务导航项自适应布局容器。

## Roles / Permissions

MVP 不新增角色或权限模型。

如果用户无某个页面权限，菜单项的最终展示策略待后续权限需求定义；MVP 可以先按现有页面可访问范围展示。

## Data / State Requirements

- 需要一份可维护的导航配置，包含工作区 key、标题、图标、默认路由、二级导航配置、二级路由上下文需求、Agent 描述和可选提示状态。
- 需要记录当前路由归属的工作区，用于一级选中态和二级导航展示。
- 需要记录导航节点的父子关系，用于二级导航、选中态、扩展子路由体系和上下文切换回退。
- 需要为二级路由节点声明上下文需求；三级及以下子路由必须从所属二级路由继承上下文需求，且不允许覆盖。
- 需要为导航节点声明回退链或安全 fallback 页面。
- 需要记录每个工作区最近使用的账号、应用、环境上下文。MVP 使用 localStorage 跨刷新保持。
- 需要从导航配置或路由元数据生成 Agent 可用的导航上下文。
- 需要提供账号、应用、环境选择器使用的最小上下文状态，并表达账号 > 应用 > 环境的层级依赖。

## Edge Cases

- 直接访问二级页面 URL 时，应能反推出所属工作区并显示正确选中态。
- 当前路由不属于任何工作区时，应落入辅助入口或保持无二级导航状态。
- 工作区最近上下文已失效时，应基于账号、应用、环境层级重新校验，并回退到可选择入口。
- 顶部上下文变化后当前页面意图不再可达时，应先尝试逐层回退；无法判断时回退到安全 fallback 页面。
- 父导航节点可达但子导航节点不可达时，应优先回退到父节点默认页。
- 三级及以下子路由如需上下文，应继承所属二级路由上下文配置；如果需要不同上下文，应调整二级路由设计，而不是在深层子路由覆盖。
- Agent 请求的目标页面需要参数但用户未提供时，应追问或跳转到列表页，不生成无效 URL。
- 折叠态下应保留图标识别和选中态，避免只靠文字识别。

## Open Questions

- “事务”工作区是否进入首个实现切片，还是等审批能力明确后再加入？
- 辅助入口应作为一级工作区、底部分组，还是进入右上角用户菜单？
- 二级导航是与一级窄栏并列常驻，还是仅当前工作区展开时显示？
- 权限不可见页面的菜单项策略需要后续权限设计确认。
- 自动逐层回退的首个实现范围需要在 plan 阶段进一步拆分。

## Acceptance Criteria

- 侧边导航一级入口按工作区组织，而不是继续以所有页面平铺为主。
- 点击一级工作区后，能够进入该工作区默认页，并向目标工作区、子应用和具体业务页面提供上次访问时相同的上下文信息。
- 当前路由能正确高亮所属一级工作区。
- 当前工作区有二级导航配置时，能展示并高亮当前二级导航项。
- 工作区切换不会主动清空顶部账号、应用、环境上下文。
- 导航配置引用统一路由对象或 route key，不引入新的硬编码 URL 列表。
- 新增工作区或二级导航项时，不需要同时修改侧边栏、顶部上下文导航和 Agent prompt 的多份重复配置。
- 新增父路由下的子路由体系时，可通过一级工作区、二级路由和深层子路由的层级关系完成导航注册。
- 导航元数据能在二级路由层表达上下文需求，并表达父子关系、回退链和安全 fallback 页面。
- 顶部上下文切换后的保活和回退概念在导航配置中有稳定表达。
- Agent 可从导航元数据理解可用导航目标、所属工作区、route key、参数和上下文需求。
- Agent 发起导航后，页面路由、侧边栏选中态和顶部上下文状态保持一致。
- 顶部账号、应用、环境选择器具备最小可用交互，能够按账号 > 应用 > 环境层级驱动当前上下文变化。
- 当前已有 MVP 页面入口仍然可达。
- 侧边导航布局组件与业务导航配置 / 导航项组件分离。
